## compaction

### auto-compact时的background subagent处理

检查现在 auto-compact 时的 background subagent 处理，确保将尚未运行完毕的 background subagent 的信息保留至 compacted 的下一轮

### compact 提示词特殊改造

因为黑板的存在，部分 compact 内容可以被黑板内容替代，针对 CTF 场景，对 pi 默认的 compact prompt 进行改造

## 黑板改造

黑板还是分两部分：

- evidence：100%确定的客观事实（例如发现并确认漏洞点、确认了某项技术可行/不可行）
- opportunities：记录可能的推进机会，解题方向，在**经过尝试**确认不行后可标记为死路，但仍留在黑板上（任何不需要实验就能确定不可能的方向不应当记录到黑板）

将记录黑板写进系统提示词，要求 solver 在取得进展后或在执行某方面/某几个方面的探索前写入黑板。

## 重构比赛调度系统

### block 改造

现在的调度系统将例如网络错误等异常停止也计入 block 计数，这是不正确的。我设计了一套新的 block 机制：

每道题目最多同时对应一个 Solver Agent, 在系统提示词明确表明：在你成功获取正确 flag 前，永远不要停下来，除非你认为自己无法完成此任务。

每个 Solver Agent 内部定义一个 block 计数，每当对话 compact 一次，计数 +2，每当对话因为非网络错误等外部原因停止时，计数 +1。

每个 turn 都检测计数是否大于阈值（默认为8），若一 turn 导致计数大于阈值，分情况进行收尾操作：

- 异常停止：如果有 subagent，要求 foreground subagent 立即汇报，要求 solver agent 立即停止并获取 background subagent 的信息；随后提示 solver 已经陷入卡住的状态，要求将目前最新进度写入黑板并停止，标注为 blocked
- 到达 auto-compact 边界：不进行 compact + 下一轮，随后提示 solver 已经陷入卡住的状态，要求将目前最新进度写入黑板并停止，标注为 blocked

标注为 blocked 后若有必要就可以销毁 js 对象，后续需要复活时从本地 session 重建，节省内存，任何 agent 都要保证重建与销毁时的一致性，这一点应该体现在测试。

### 并发上调

默认并发 solver 数上调至 8

### 调度

先按最高并发数启动例如八个 solver，一旦有解出/blocked，压入排队的题目。最终剩下的只有 blocked 的题目后，才按 block 的先后顺序，先 block 的先复活，用存储的黑板的内容起一个全新的 session 重试，每次“复活”都会上调4点仅针对于此题的 block 阈值。

### 人工介入

可以在 webui 对队列中的题目顺序做调整，这个调整可以无视 block 题目滞后的限制

## 重构 Solver

solver 在解出并写完 wp 后就可以销毁沙盒，仅保留 workspace 文件了。

### 人工介入

webui 显示更加详细的信息（题目 tldr，黑板内容，附件下载，现有工作区文件预览/工作区文件下载）便于人工介入，提供 steer 和 followup 模式

tldr 可以派生一个 tldr agent 负责，tldr agent session 会持久化，和 solver share 一个沙盒，但是不具有写能力。
启动时使用廉价模型生成一次 tldr，保存 session 后销毁对象防止占用，后续可以通过 webui 主动触发更新（恢复 tldr agent，发送一条更新 prompt，更新输出）

### WriteUps 编写

在提交 flag 并检验正确后，向指定位置输出 writeup.md，这个 wp 可以在 webui 渲染并查看，也可以在 webui 导出所有题目的 writeup。

writeup 应当遵循一定的书写格式。
