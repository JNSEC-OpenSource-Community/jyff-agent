# CTF Agent 重构实现方案

> 状态：实现前设计稿
>
> 目标读者：后续负责实现、评审、测试和补充提示词的 Agent 或开发者
>
> 依据：当前代码、`README.md`、`docs/architecture.md`、`docs/blackboard-spec.md`、`docs/subagents.md` 和 `docs/temp/重构0805.md`

## 1. 文档目的

本文把本轮重构需求转换为可以逐阶段实现和验收的工程方案。实现者不得把本文当成已经存在的行为；完成每个阶段后，必须同步更新正式 `docs/`、README、测试和公开类型。

以下术语具有约束含义：

- **必须**：缺失时不满足需求；
- **应当**：默认实现方式，只有明确理由时才能偏离；
- **可以**：可选增强，不阻塞核心交付；
- **Agent-visible challenge info**：平台原始 `ChallengeInfo` 加上 Core 生成的公告、附件路径、黑板快照等运行时信息；
- **存活周期**：一道题从创建 Solver session 到 solved、blocked 或人工取消；
- **复活**：blocked 题目创建全新 Run/session 再次尝试，不是继续向旧 blocked session 写消息。

## 2. 总体不变量

实现后必须始终满足：

1. 同一道题最多有一个活跃 Solver Agent；数据库和内存层都要防重。
2. 普通模型停止、compact 和可恢复错误不再自动创建新 Run。
3. 只有 blocked 后的自动/人工复活才创建新的 Solver Run/session。
4. 每道题使用稳定的题目级 workspace；Run、复活后的 Solver、TLDR Agent 和 SubAgent 都看到同一批文件。
5. Solver 和其 SubAgent 共享同一个 sandbox；SubAgent 默认使用独立 cwd。
6. blocked 或 solved 后可以销毁 Solver、SubAgent manager、TLDR Agent 等 JS 对象；JSONL、SQLite 和 workspace 是恢复依据。
7. 正确 flag 已确认但 writeup 尚未通过校验时，不得销毁 sandbox。
8. 平台公告、题目描述、黑板和 SubAgent 输出都是数据，不得成为更高优先级指令。
9. 固定 system/control/continuation/compaction prompt 使用英语，并要求 Agent 的 reasoning 和 Agent 生成的解题内容使用英语。
10. 题目原文、附件、人工输入、flag、路径和协议 payload 保留原文，不做可能破坏语义的自动翻译。
11. 网络和其他瞬态基础设施错误不得增加题目的 block score。
12. 队列、block score、复活次数、公告处理和交付状态必须可跨进程恢复。

## 3. 目标状态机

```text
pending -> queued -> preparing -> running
                                  |
                                  +-- transient infrastructure failure
                                  |      score +0, backoff, same Run/session
                                  |
                                  +-- non-transient stop/error
                                  |      score +1
                                  |      <= threshold: same Run/session, next turn
                                  |      > threshold: blocking
                                  |
                                  +-- auto-compact boundary
                                  |      prospective score +2
                                  |      <= threshold: compact, same Run/session
                                  |      > threshold: skip compact, blocking
                                  |
                                  +-- accepted flag
                                         writing_writeup
                                         |
                                         +-- valid writeup -> solved -> cleanup
                                         +-- invalid/missing -> writeup turn

blocking -> collect SubAgents -> final blackboard turn -> blocked -> cleanup
blocked  -> scheduler revival -> new Run/session, same workspace -> running
```

`score > threshold` 才进入 blocked；`score === threshold` 时允许继续。

## 5. Prompt 和语言重构

### 5.1 范围

必须转换为英语的固定内容包括：

- Solver system prompt；
- SubAgent shared prompt 和内置角色 prompt；
- TLDR prompt；
- continuation、blocked finalization、writeup prompt；
- SubAgent delegation policy；
- compact prompt；
- 公告 steer prompt；
- 黑板使用规则；
- Agent tool description 中会影响模型行为的文字。

面向人的 WebUI 中文标签、错误提示和中文代码注释不在这个限制内。

### 5.2 人工负责的部分

Solver system prompt、SubAgent 角色正文和委派 prompt 最终由人类编写。实现者只应：

1. 建立 `PromptBundle`/prompt version 接口；
2. 提供清楚的 placeholder 和英文临时占位文案；
3. 为动态字段做 XML/JSON 编码；
4. 添加 prompt snapshot 测试；
5. 不自行把角色行为扩展为未经确认的策略。

### 5.3 静态检查

为固定 prompt 目录添加测试，检测 Unicode Han 字符。以下内容允许例外：

- 动态题目原文；
- 公告原文；
- 人工消息；
- 用户自定义角色正文；
- 错误消息和 UI label。

模型是否真的使用英语思考无法由单元测试完全证明；测试只验证 prompt 明确包含该要求，E2E 再抽样检查可见 reasoning 输出。

## 6. Compaction 重构

### 6.1 取消隐式 compact

当前 `BaseAgent.prompt()` 在 prompt 前直接调用 `compactIfNeeded()`。应改为：

- BaseAgent 提供只读 `contextPressure()`；
- Solver supervisor 在每个新 turn 前检查；
- supervisor 决定 compact、block 或继续；
- BaseAgent 不再自行改变 block score 或生命周期。

### 6.2 block score 与 compact

到达 auto-compact 边界时，supervisor 先以幂等事件尝试增加 2 分：

```text
scoreAfter = scoreBefore + 2
```

- `scoreAfter <= threshold`：执行 compact，并记录 `compact_performed=true`；
- `scoreAfter > threshold`：记录 `compact_performed=false`，不调用 Pi compact，进入 blocking。

虽然第二种情况没有真正执行 compact，边界事件仍消耗 2 分，否则无法表达“该边界导致超过阈值”。

### 6.3 CTF compact 内容

compact prompt 应要求只保存黑板无法替代的信息：

- 当前具体目标；
- 自最近一次黑板更新后的未记录发现；
- 未完成实验及其精确状态；
- 关键路径、命令、地址、常量、凭据来源和候选 flag；
- 人工 steer/followup；
- 活跃 SubAgent 任务和等待中的结果；
- 下一步最小可执行动作。

它不应完整复制已经存在于黑板的 Evidence 和 Opportunity，只引用 ID 或说明尚未写入的变化。

### 6.4 compact 后注入

compact 成功后追加最新数据消息：

```xml
<challenge_blackboard encoding="json">...</challenge_blackboard>
<active_subagents encoding="json">...</active_subagents>
<challenge_announcements encoding="json">...</challenge_announcements>
```

这些消息都必须标明为不可信数据。

### 6.5 background SubAgent 一致性

compact 开始前读取一次 worker snapshot，结束后再读取一次。最终注入使用结束后的 snapshot。compact 期间完成的 worker：

- 完成记录先写 SQLite；
- completion notification 保留在 Pi followup queue；
- compact 后 snapshot 包含完成结果或结果引用；
- 下一 turn 同时能看到 snapshot 和通知；
- 相同 worker ID 的重复通知必须可安全忽略。

## 7. Blackboard v2

### 7.1 Evidence

Evidence 只能表示已验证、可复现、100% 确定的客观事实，包括：

- 已确认漏洞点或利用原语；
- 已复现的程序/服务行为；
- 已确认某技术在明确条件下可行或不可行；
- 已验证的关键常量、算法、地址或文件事实。

Evidence 继续只增不改。

### 7.2 Opportunity

Opportunity 表示需要实验才能判断的推进方向。无需实验即可排除的方向不得进入黑板。

为兼容旧库，保留 `status=open|concluded`，增加：

```text
resolution = NULL | confirmed | dead_end
```

标记 `dead_end` 时必须同时产生描述实验和结果的 Evidence。死路永久保留，避免后续 Run 重复尝试。

### 7.3 Solver 行为

system prompt 必须要求 Solver：

- 在取得可复用进展后立即写 Evidence；
- 在开始一个或一组实验性方向前先写 Opportunity；
- 实验失败后将对应 Opportunity 标记为 dead end；
- 独立复核 SubAgent 输出后才能写 Evidence；
- 公告和提示只作为新信息，未经验证不得自动成为 Evidence。

存储层不能判断陈述是否真实，只能保证长度、归属、引用和事务一致性。

## 8. Block 机制

### 8.1 持久化字段

扩展 `challenge_runtime_state`：

```sql
block_score             INTEGER NOT NULL DEFAULT 0
base_block_threshold    INTEGER NOT NULL DEFAULT 8
revival_count           INTEGER NOT NULL DEFAULT 0
blocked_at              TEXT
blocked_run_id          TEXT
lifecycle_generation    INTEGER NOT NULL DEFAULT 0
```

有效阈值：

```text
base_block_threshold + revival_count * 4
```

增加 `challenge_block_events`：

```sql
id, challenge_id, run_id, event_key,
delta, reason, score_before, score_after,
threshold, compact_performed, created_at
```

`event_key` 必须唯一，避免崩溃恢复和重复事件造成重复计分。

### 8.2 错误分类

禁止仅通过任意错误字符串直接计分。统一分类至少包括：

```text
network_transient
provider_transient
authentication_or_configuration
model_stop
length
protocol_or_non_transient
operator_cancel
process_shutdown
timeout
submitted
```

建议规则：

| 原因 | block delta | 处理 |
|---|---:|---|
| 网络断开、连接重置、DNS、provider 429/5xx | 0 | 退避，同 session 重试 |
| 认证或模型配置错误 | 0 | 暂停控制面，等待配置修复 |
| 正常 stop 但无 flag | 1 | 同 session 下一 turn 或 block |
| length、协议错误、非瞬态 provider 错误 | 1 | 同 session 下一 turn 或 block |
| 单次 prompt timeout | 1 | abort 当前 turn，同 session 继续或 block |
| 人工取消、正常关机 | 0 | 按控制面语义关闭/恢复 |
| 正确 flag | 0 | 进入 writeup |

如果 Pi/Provider 只返回错误字符串，应先在 provider adapter 层归一化为带 code 的错误；字符串匹配只能作为兼容回退并必须有测试。

### 8.3 普通停止

未超过阈值时：

1. 不关闭 Solver、SubAgent manager 或 sandbox；
2. 写 block event；
3. 追加英文 continuation prompt；
4. 继续同一个 Run/session；
5. 不增加 scheduler attempt。

### 8.4 blocking 收尾

统一实现 `finalizeBlockedRun()`：

1. 事务更新 Run 为 `blocking`；
2. 向所有 running SubAgent 发送英文 final-report steer；
3. foreground worker 立即结束当前调查并汇报；
4. background worker 在短 grace period 内返回；
5. 收集 completed/failed/running/queued 状态和已有输出；
6. 将结果作为数据注入 Solver；
7. 启动受限最终 turn，只保留黑板、结果读取和必要文件读取能力；
8. 要求 Solver 把最新进度、机会和死路写入黑板后停止；
9. 最终 turn 失败也必须标记 blocked，并记录 `block_finalization_failed`；
10. 关闭 worker、远程实例和 sandbox；
11. 删除内存对象，保留 JSONL、SQLite 和 workspace。

compact 边界触发 blocking 时不得先 compact。应依赖 Pi 的 reserve context 完成最后一次短 prompt。

### 8.5 恢复与复活的区别

- **进程恢复**：非终态 Run 从原 JSONL session 重建同一存活周期，保持 `runId`；
- **blocked 复活**：旧 blocked Run 保持只读，创建全新 Run/session，复用 workspace 并注入黑板。

测试必须证明重建前后 model、thinking、tools、session path、workspace、SubAgent session 和状态一致。

## 9. 调度器 v2

### 9.1 默认并发

生产默认 `maxConcurrent` 从 2 改为 8；CLI、scheduler config、README、Compose 环境说明和 WebUI 默认值必须同步。

### 9.2 持久化队列

新增 `scheduler_queue`：

```sql
challenge_id, source, lane, position,
manual_override, enqueued_at, version
```

`lane` 至少有：

```text
normal
blocked
```

队列领取、移动、删除和 Run 创建必须使用事务。为 active Run 增加按 `challenge_id` 的 partial unique index，从数据库层保证同题唯一。

### 9.3 自动策略

1. 启动时先按队列顺序填满 8 个普通 Solver；
2. 任一题 solved/blocked 后立即补入下一道普通题；
3. 只要还有普通 pending/queued/active 题，就不自动领取 blocked lane；
4. 普通题耗尽后按 `blocked_at ASC` 复活；
5. 多个空槽可以依次领取多个 blocked 题，但顺序必须稳定；
6. 每次复活先在事务中 `revival_count += 1`，因此该题阈值增加 4；
7. 人工排序可以设置 `manual_override=true`，允许 blocked 题越过 normal lane；
8. 自动复活不清零 block score。

旧 `maxAttempts` 不再限制解题轮次。可以删除，或只用于 sandbox/platform 准备失败；不得与 block 机制重复限制。

### 9.4 WebUI API

推荐：

```http
PATCH /api/scheduler/queue/:challengeId
Content-Type: application/json

{
  "position": 1,
  "expectedVersion": 17,
  "overrideBlockedLane": true
}
```

版本冲突返回 409，前端刷新后重试，避免两个操作者互相覆盖。

## 10. 题目级 workspace

workspace 应从 Run 级改为题目级稳定目录：

```text
.ctf-agent/challenges/<safe-key>/workspace/
```

`safe-key` 使用稳定 hash 或经过严格编码的 ID，不能直接信任平台 challenge ID。

要求：

- 每次 Run 的 `runs.workspace` 可以指向同一路径；
- 附件下载幂等，文件名冲突有确定策略；
- Solver、复活后的 Solver、SubAgent 和 TLDR Agent 使用同一挂载；
- sandbox 销毁不删除 workspace；
- solved 后保留 workspace；
- 写入和下载 API 拒绝路径逃逸和符号链接越界。

## 11. Flag 与 Writeup

### 11.1 生命周期

`ctf_submit_flag` 收到 `accepted` 或 `already_solved` 时不再 `terminate: true`。改为：

1. 保存 terminal submission；
2. Run 进入 `writing_writeup`；
3. 禁用再次提交 flag 和远程实例变更；
4. 要求 Solver 写 `/workspace/writeup.md`；
5. 控制面校验格式；
6. 不合格则继续专用 writeup turn，不增加 block score；
7. 合格后标记 solved 并销毁 sandbox。

### 11.2 Writeup 格式

至少包含：

```markdown
# <Challenge Title>

## Summary
## Analysis
## Vulnerability or Weakness
## Solution / Exploitation
## Reproduction
## Relevant Artifacts
## Flag
```

要求记录关键命令、脚本路径和可复现步骤。校验器只验证存在、大小、UTF-8 和必需标题，不判断技术内容真假。

### 11.3 WebUI

- 安全渲染 Markdown；
- 单题查看/下载；
- 导出全部题目的 writeup ZIP；
- 缺失或校验失败时显示明确状态。

## 12. TLDR Agent

### 12.1 持久化

```text
.ctf-agent/challenges/<safe-key>/tldr/session.jsonl
```

SQLite 保存最新 TLDR、模型、更新时间和错误。

### 12.2 能力

- 使用独立、可配置的廉价模型；
- 与活跃 Solver 共享 sandbox；
- 只有 `read`、`list` 和只读黑板工具；
- 不提供 `bash`、`write`、`edit`、flag、实例或 SubAgent 管理工具；
- 首次生成后销毁 JS 对象；
- WebUI 触发更新时从 JSONL 恢复并发送英文 update prompt；
- Solver 已关闭时创建挂载同一 workspace 的临时只读 sandbox。

TLDR 至少覆盖题目摘要、附件、确认事实、开放机会、死路、重要 workspace 文件和人工接手建议。

## 13. 公告定时抓取与 Solver 注入

### 13.1 目标行为

控制面必须定时调用平台 `listAnnouncements()`：

1. 过滤一血、二血、三血、首杀和其他解出播报；
2. 对剩余公告检测题目标题；
3. 命中后把公告附加到该题的 Agent-visible challenge info；
4. 未来创建/复活/恢复的 Solver 在 challenge context 中看到这些公告；
5. 如果命中题目已有活跃 Solver，立即 steer 一条包含公告的消息；
6. 公告抓取失败不影响 Solver，不增加 block score；
7. 处理、匹配和交付都必须幂等且可恢复。

### 13.2 所属生命周期

公告 poller 必须位于 Core/ControlPlane，不得依赖 WebUI snapshot timer。原因：

- headless runner 也需要公告；
- WebUI SSE/刷新频率不应决定平台 API 请求频率；
- ControlPlane 可以统一处理连接、断线、关闭和重连。

建议流程：

```text
ControlPlane ready
  -> initial announcement baseline
  -> start scheduler
  -> setTimeout-based poll loop
  -> stop/disconnect cancels loop
```

使用递归 `setTimeout`，避免上一轮未完成时重叠执行。默认间隔建议 30 秒，允许 WebUI 配置 5–3600 秒，失败时指数退避，成功后恢复正常间隔。

### 13.3 平台公告类型增强

扩展 `Announcement`，保持字段向后兼容：

```ts
type AnnouncementKind =
  | "normal"
  | "hint"
  | "new_challenge"
  | "solve_broadcast"
  | "unknown"

interface Announcement {
  id: string
  title: string
  content: string
  publishedAt: string
  kind?: AnnouncementKind
  rawType?: string
}
```

GZCTF 必须把 `FirstBlood`、`SecondBlood`、`ThirdBlood` 映射为 `solve_broadcast`；`NewHint` 映射为 `hint`。CTFd 没有稳定类型时由 Core 文本分类器补充判断。

不要让 Platform 插件负责题目匹配；插件只归一化平台事实。

### 13.4 Solve broadcast 过滤

优先顺序：

1. `kind === solve_broadcast`：直接过滤；
2. 已知 `rawType`：按明确 allow/deny map；
3. 标题结构匹配：`一血|二血|三血|首杀|First Blood|Second Blood|Third Blood`；
4. 内容仅在符合“队伍/用户 + 解出动作 + 题目”的播报结构时过滤，例如 `solved by`、`成功解出`、`解出了`；
5. 不做过宽的单关键词过滤，避免真实 hint 中提到“一血机制”时被误删。

分类结果和原因应持久化。被过滤公告默认不进入 Solver，也不出现在 Solver 公告列表；WebUI 可以在诊断视图显示 ignored 记录。

### 13.5 公告持久化

增加：

```sql
CREATE TABLE IF NOT EXISTS contest_announcements (
  announcement_key TEXT PRIMARY KEY,
  platform_announcement_id TEXT NOT NULL,
  revision_hash TEXT NOT NULL,
  title TEXT NOT NULL,
  content TEXT NOT NULL,
  published_at TEXT NOT NULL,
  kind TEXT NOT NULL,
  classification_reason TEXT,
  ignored INTEGER NOT NULL DEFAULT 0,
  first_seen_at TEXT NOT NULL,
  last_seen_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS challenge_announcements (
  challenge_id TEXT NOT NULL,
  announcement_key TEXT NOT NULL,
  match_type TEXT NOT NULL,
  matched_value TEXT NOT NULL,
  created_at TEXT NOT NULL,
  PRIMARY KEY (challenge_id, announcement_key)
);

CREATE TABLE IF NOT EXISTS announcement_deliveries (
  challenge_id TEXT NOT NULL,
  announcement_key TEXT NOT NULL,
  run_id TEXT NOT NULL,
  status TEXT NOT NULL,
  attempts INTEGER NOT NULL DEFAULT 0,
  queued_at TEXT,
  observed_at TEXT,
  last_error TEXT,
  PRIMARY KEY (challenge_id, announcement_key, run_id)
);
```

公告可能被平台原地编辑，因此 `announcement_key` 应由平台 ID 和内容 revision hash 组成。相同内容重复拉取不得产生新记录或重复 steer；内容变化视为新 revision。

### 13.6 初始 baseline

首次连接时：

- 拉取当前全部公告；
- 分类、匹配并持久化；
- 不对尚未启动的 Solver steer；
- scheduler 必须在 baseline 完成后启动，因此新 Solver 的初始 challenge info 已包含历史有效公告；
- 进程恢复时也先完成 baseline，再恢复 active Solver。

这样既不丢历史 hint，也不会在启动后向大量 Solver 重放所有旧公告。

若 baseline 失败，记录 degraded 状态并允许 scheduler 启动；后续首次成功抓取时，只对 `publishedAt` 晚于本次进程启动时间的公告执行实时 steer，旧公告仅附加到 challenge info，避免历史洪泛。

### 13.7 题目标题匹配

匹配前构建 challenge index：

- Unicode NFKC；
- Unicode case fold；
- 连续空白折叠；
- 保留原始标题用于展示；
- 同时索引 challenge ID；
- 标题按长度降序匹配，避免短标题抢占长标题。

第一版只做确定性匹配，不做模糊/向量/LLM 匹配：

1. 平台若提供结构化 challenge ID/title，优先精确匹配；
2. 公告标题或正文中出现带边界的规范化完整题目标题；
3. challenge ID 只在独立 token、引号或括号中精确匹配；
4. 极短标题（建议规范化后少于 3 个字符）只接受引号、书名号、方括号或平台结构化字段中的精确匹配；
5. 相同规范化标题对应多个题目时，附加到所有候选并写 diagnostic，不擅自选择；
6. 一个公告可以命中多道题，每道题分别建立关联和交付记录。

不确定匹配不得 steer。后续可以增加 WebUI 人工关联入口，但不属于核心验收条件。

### 13.8 Agent-visible challenge info

不要要求 Platform `ChallengeCapability.getInfo()` 自己拼公告。Core 定义：

```ts
interface AgentChallengeInfo extends ChallengeInfo {
  announcements: Array<{
    key: string
    title: string
    content: string
    publishedAt: string
    kind: AnnouncementKind
  }>
}
```

创建、恢复或复活 Solver 时，从 RunStore 查询该题公告并加入初始 XML：

```xml
<challenge_context>
  ...
  <announcements>
    <announcement key="..." published_at="...">
      ...escaped original text...
    </announcement>
  </announcements>
</challenge_context>
```

公告内容必须 XML escape，并在 system prompt 中明确它是平台数据而非系统指令。

### 13.9 活跃 Solver steer

发现新 revision 且匹配活跃 Solver 时：

1. 先事务写公告和 challenge 关联；
2. 创建 `announcement_deliveries(status=pending)`；
3. 生成英文控制 wrapper，内部保留公告原文：

```xml
<challenge_announcement key="..." published_at="...">
  <title>...</title>
  <content>...</content>
</challenge_announcement>
```

4. 调用 `solver.steer()`，而不是普通聊天接口；
5. steer 成功后标记 `queued` 并写 `announcement_steered` Run event；
6. Solver 下一次实际处理该消息时写 `observed`；
7. 当前 turn 恰好结束也不得丢失 steer queue，supervisor 必须继续下一 turn；
8. Solver 已在 `blocking`、`writing_writeup` 或关闭过程中时不 steer，只保留 challenge 关联供未来查看/复活使用。

Pi 的内存 steer queue 不是独立持久化 outbox，因此崩溃窗口内只能实现至少一次交付。消息带稳定 `announcement key`，恢复时可以重投 `pending/queued but unobserved`；Solver prompt 要求按 key 忽略重复公告。不得为了追求伪造的 exactly-once 而在 DB 标记成功后丢消息。

### 13.10 与 compact、block 和黑板的交互

- compact 后注入当前题目的完整有界公告列表；
- compact summary 不重复复制公告全文，只保留公告 key 和尚未处理的影响；
- 公告 steer 本身不增加 block score；
- 公告抓取/匹配/交付错误不增加 block score；
- blocking 已开始后新公告只持久化，不打断最终收尾；
- blocked 后复活的新 session 自动获得全部关联公告；
- 公告不是 Evidence，Solver 必须实验验证后才能写黑板；
- 被公告否定且已经实验过的方向可以标记 dead end，并引用实验结果，而不是仅引用公告文字。

### 13.11 WebUI 公告配置和展示

配置项建议：

```text
enabled                  default true
pollIntervalSeconds      default 30, range 5..3600
hideSolveBroadcasts      fixed true for Solver delivery
additionalIgnorePatterns optional, bounded
```

WebUI 题目详情显示：

- 命中公告列表；
- 公告发布时间和类型；
- 是否已 steer 到当前 Run；
- 匹配依据；
- 交付失败诊断。

Secret 不属于公告配置。自定义正则必须限制长度和数量，并避免可造成 ReDoS 的执行方式；更安全的第一版只支持普通 case-insensitive substring。

## 14. WebUI 人工介入

题目详情至少展示：

- 原始题目信息和 TLDR；
- 当前 block score、阈值、复活次数；
- Evidence、open Opportunity、confirmed、dead end；
- 相关公告；
- 附件下载；
- workspace 文件树、文本预览和文件下载；
- writeup 渲染和下载；
- Run/SubAgent 状态、结果和错误。

人工消息 API 必须显式区分：

```json
{ "mode": "steer", "text": "..." }
{ "mode": "followup", "text": "..." }
```

- `steer`：尽快在当前 turn 边界影响执行；
- `followup`：排入当前工作完成后的下一轮；
- 两者都先写 Run event，并携带 mode；
- 没有活跃 Solver 时返回 409，不隐式复活；
- blocked 复活使用单独操作。

### 14.1 文件安全

所有 workspace/附件/writeup API：

- 使用 `resolve()` 后验证仍位于题目 workspace；
- 拒绝绝对路径、`..`、NUL 和 symlink 越界；
- 预览有大小上限并区分文本/二进制；
- 下载设置正确 MIME、长度和 `Content-Disposition`；
- 不把宿主机绝对路径返回浏览器；
- ZIP 由受控库生成，不拼 shell 命令。

## 15. pi-web-access fork

fork 必须作为纯 Agent tool library 接入，而不是 Pi TUI extension：

```ts
createWebAccessTools(config): AgentTool[]
```

保留候选工具：

- `web_search`；
- `fetch_content`；
- `get_search_content`；
- `source_check`。

必须移除/禁用：

- Commands；
- shortcuts、widget、activity UI；
- curator browser UI；
- 自动打开浏览器；
- Gemini Web；
- Chromium cookie 读取；
- `allowBrowserCookies` 和相应环境变量入口。

Gemini API 可以保留。默认 workflow 使用无 TUI 的 `none` 或 `auto-summary`。Provider 使用显式 allowlist，WebUI 配置密钥进入现有 Secret Store，读取 API 只返回配置状态。

GitHub clone、PDF 和搜索结果临时文件必须位于 sandbox 可见的题目 workspace；无法保证时应禁用相应本地路径功能。保留 SSRF、私网地址拦截、超时、取消和输出限制。依赖固定 fork commit/version。

## 18. RunStore 迁移

迁移必须保留 `CREATE TABLE IF NOT EXISTS` 和旧数据库兼容。建议顺序：

1. 创建新表；
2. 对旧表使用 `PRAGMA table_info` 检查并 `ALTER TABLE ADD COLUMN`；
3. 将旧 `session_interruptions` 映射为初始 `block_score`；
4. 旧 `blocked=1` 至少映射为默认阈值加一；
5. 创建 partial unique index 前先诊断重复 active Run；
6. 一个事务内修复或标记遗留 active Run；
7. 保留 legacy 字段用于审计，正式文档注明不再写入；
8. 所有迁移都要有“旧 DB fixture -> 新版本打开 -> 数据保持”测试。

建议新增 Run 状态：

```text
blocking
writing_writeup
```

建议新增 Run source：

```text
revival
```

## 20. 测试矩阵

### 20.1 Compaction

- running background worker 跨 compact 保留；
- worker 在 compact 期间完成；
- completion notification 不丢失且可去重；
- prospective score 超阈值时不调用 compact；
- compact 后黑板和公告使用最新快照；
- compact event 重放不重复计分。

### 20.2 Block 和恢复

- stop/length/timeout 正确 +1；
- 网络、429、5xx、认证配置错误 +0；
- `score === threshold` 继续，`score > threshold` blocking；
- foreground/background final report；
- finalizer 失败仍 blocked；
- close/cleanup 幂等；
- JS 对象销毁后从 JSONL 重建一致；
- 同题不能出现两个 active Solver。

### 20.3 调度

- 初始填满 8 个；
- solved/blocked 后即时补位；
- normal 未耗尽时不复活 blocked；
- blocked 按 `blocked_at`；
- 每次复活阈值加 4；
- 人工重排越过 lane；
- 重启后队列顺序不变；
- 并发领取不重复。

### 20.4 Blackboard

- Evidence 只增；
- open -> confirmed/dead_end；
- dead_end 与 result Evidence 同事务；
- 跨题引用拒绝；
- 旧 concluded 数据迁移；
- snapshot 截断提示仍正确。

### 20.5 公告

- GZCTF First/Second/ThirdBlood 被过滤；
- CTFd 中英文解出播报被保守过滤；
- 普通公告和 hint 不误删；
- Unicode、大小写、空白和标点规范化；
- 长标题优先、短标题边界；
- 同名题 diagnostic；
- 一个公告命中多题；
- 重复 poll 不重复关联/steer；
- 编辑公告产生新 revision；
- initial baseline 不洪泛 steer；
- baseline 后的新公告 steer 活跃 Solver；
- inactive/blocked/writing_writeup Solver 只附加 challenge info；
- poll 网络失败不修改 block score；
- steer 崩溃窗口恢复时至少一次交付；
- compact 后公告仍存在；
- 公告中的 prompt injection 只能作为数据。

### 20.6 Writeup/workspace/WebUI

- accepted 后 sandbox 仍存在；
- writeup 合格后 sandbox 才销毁；
- 缺失/不合格继续 writeup turn；
- workspace 在复活后保持；
- 文件 API 拒绝 `..`、绝对路径和 symlink；
- 二进制预览受限；
- writeup Markdown 安全渲染；
- 全部 writeup ZIP 可打开。

### 20.7 TLDR/SubAgent/web-access

- TLDR 无写工具；
- TLDR session 恢复一致；
- TLDR 与 Solver 共享 workspace；
- 角色 model/thinking 覆盖和 fallback；
- SubAgent 与 Solver sandbox ID 相同；
- Gemini Web/browser cookie/Commands/TUI 无法启用；
- web-access secret 不出现在 API 和事件中。
